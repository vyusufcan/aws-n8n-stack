n8n on AWS
Infrastructure & Automation

A production-grade n8n deployment built on a split-stack Terraform model — stateful storage, a k3s cluster, and the application layer each live in their own boundary so any layer can be rebuilt without touching the others.

On top of the infrastructure, two n8n workflows provide AI-driven Kubernetes operations: one for on-demand SRE chat and one for autonomous alert investigation.

Design Rationale

Why split the infrastructure into separate stacks?

Most people run everything in one Terraform root. That works until you need to replace the app server — at which point your data, your cluster, and your compute all live and die together.

  • Persistent data stays safe. The EBS volume lives in its own storage/ stack. Destroying the app instance never touches it.
  • The cluster stays decoupled. k3s/ publishes its details into SSM so the app can discover them at boot time without hard-coded addresses.
  • Rebuilds become routine. infra/ can be torn down and recreated in a single apply. No data migration, no manual re-wiring.
  • Blast radius is small. A bad infra/ change cannot accidentally destroy the volume or the cluster.

Stack Layout

Four ownership boundaries, one dependency chain

1 · bootstrap

Creates the S3 bucket that holds remote Terraform state for all other stacks. Run once, never touch again.

2 · storage

Owns the persistent encrypted EBS volume mounted at /srv/n8n. This is the only stack that should never be destroyed.

3 · k3s

Provisions a standalone k3s EC2 server and writes its private IP and kubeconfig path to SSM Parameter Store.

4 · infra

Builds the app EC2 host, ALB, Route53 records, IAM profile, and attaches the volume. Reads k3s details from SSM at plan time.

Traffic & Networking

How a request gets from the internet to n8n

  • Route53 resolves n8n.vyusufcan.cloud and chat.vyusufcan.cloud to the ALB.
  • ALB accepts HTTPS on port 443, terminates TLS, and forwards based on host header — n8n traffic to port 5678, chat UI traffic to port 80.
  • Security groups are tight: the app instance only accepts those two ports from the ALB, and SSH only from the operator IP captured at apply time.
  • k3s can reach the app instance directly on port 5678, using the security group rule derived from the SSM private IP — no public exposure needed.

Data & Persistence

What survives a rebuild and what doesn't

Durable

The EBS volume holds all n8n workflow data, credentials, and execution history. It is managed by storage/, detached and reattached on each app rebuild, never deleted by infra/ teardown.

Ephemeral

The EC2 root disk is disposable. Every infra/ apply starts with a fresh Ubuntu 24.04 instance that bootstraps itself from user data, then mounts the persistent volume at /srv/n8n.

Bootstrap Process

On first boot, user_data.sh.tftpl pulls the kubeconfig from SSM, mounts the EBS volume, and starts n8n in Docker with the data path mapped to /home/node/.n8n inside the container.

SSM as Glue

SSM Parameter Store holds k3s/kubeconfig and k3s/private-ip. Both are written by the k3s stack and consumed by infra at plan time and by the app host at boot time.

n8n Automation

Two workflows that make the cluster observable

Both workflows give n8n shell access to kubectl on the app host, using the kubeconfig written to .n8n/k3s/kubeconfig.yaml during bootstrap. Both are read-only by design — no mutations allowed.

K8S SRE

A chat-driven assistant you talk to directly. Ask it what's wrong with your cluster and it investigates using kubectl, then replies in structured markdown. Available as an MCP tool.

Prometheus Alert Manager

A webhook-triggered responder. When Alertmanager fires, this workflow automatically investigates the affected pod, builds a full incident report, and emails it.

K8S SRE — the on-demand investigation agent

You open the chat UI, describe a symptom, and the agent figures out what's happening in the cluster without you having to write a single kubectl command yourself.

  • Trigger: public chat webhook — works from the n8n UI or any MCP-compatible client.
  • Model: gpt-4o with a rolling memory window of the last 10 messages so the conversation has context.
  • Tool: an Execute Command node that runs kubectl with --kubeconfig explicitly set on every call.
  • Safety rules baked into the prompt: read-only commands only, no delete / apply / exec / port-forward, max 10 kubectl calls per investigation.
  • Output: pod listings as markdown tables; all other findings as structured status, findings, commands run, and recommendations.

Prometheus Alert Manager — autonomous incident response

When Alertmanager sends a webhook, this workflow wakes up, investigates the incident without human input, and delivers a formatted report straight to your inbox.

Step 1 Receive Webhook on POST /prometheus-alert accepts the Alertmanager payload.
Step 2 Parse Extracts alertname, severity, namespace, pod, status, summary, description, and start time.
Step 3 Investigate AI agent runs read-only kubectl commands against the affected pod or node. Same safety rules as the SRE workflow.
Step 4 Report Agent outputs strict JSON — incident metadata, root cause, recommendations, and commands run.
Step 5 Email HTML incident report with severity-colored header sent via Gmail to the on-call address.
